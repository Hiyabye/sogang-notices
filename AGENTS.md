# Sogang notices development guide

## Scope and conventions

- Keep this collector separate from [Rill](https://github.com/Hiyabye/Rill). It publishes public notice-list metadata for the 41 boards in `sources.mjs`, not a runtime backend.
- Use npm, the lockfile, native Node fetch, and the built-in test runner. parse5 is the approved HTML parser; do not execute source JavaScript or add browser automation. Rill does not scrape or run this collector; its frontend dependencies are governed by its own instructions.
- Support Node 22.18+ on 22.x, or Node 24+; GitHub Actions uses Node 24. Use two-space indentation, single-quoted JavaScript strings, and semicolon-free style.
- Ask before dependencies, other boards, articles, attachments, login-only material, or persistent services. No RSS, arbitrary URL registry, plugin framework, database, or custom recovery service.
- `README.md` is for users/operators: feed behavior, commands, publication, certificate provenance, and troubleshooting. This file owns engineering invariants and verification.
- Preserve unrelated changes. Never manually edit the lockfile or generated `public/`. Do not commit output, cookies, private keys, credentials, or private source data.
- Commits, pushes, deployment, and live scheduling changes require explicit authorization. Commit format is `label: concise title`, followed by a short body. No agent attribution.

## Responsibilities and data flow

`Public university JSON / source-specific list HTML -> validated metadata and pagination -> per-board feeds -> staged public/feeds -> GitHub Pages -> Rill`

- `sources.mjs`: explicit source IDs, CMS site/board/host tuples, board pagination URLs, and fixed published recovery URLs. No user configuration.
- `collect.mjs`: main-site `buildFeed`, bounded request I/O, complete baseline validation, rolling/full orchestration, `collectSource`, two-source concurrency, recovery, final validation, staging, and workflow summary. Expected source failures use `SourceError`; programming and infrastructure faults propagate and stop publication.
- `batches.mjs`: six explicit stable memberships, per-board request estimates, catalog coverage validation and oldest-attempt selection. No wall-clock modulo or runtime rebalancing.
- `pacing.mjs`: one monotonic, serialized request-start gate per collection run. It spaces university starts by one second without serializing whole requests or pacing GitHub reads.
- `cms.mjs`: pure CMS list and newsletter-gallery parsing, including comment titles and explicit page sizes.
- `community.mjs`: Electronic/System Semiconductor PHP table and gallery skins, board headings, code/ID identity and list-title extraction.
- `mechanical.mjs`: Mechanical Engineering's server-rendered table only; never parse or execute Next.js hydration scripts or use `/api`.
- `semiconductor.mjs`: Semiconductor board identity, numbered lists and separately repeated pins.
- `html.mjs`: shared parse5 traversal, field/URL/date validation and per-page completeness checks.
- `list.mjs`: shared cross-page count/order checks, distinct regular sampling and final metadata-only selection.
- `feed.mjs`: strict schema-2 recovery/final-output validation and the explicit source-failure error type. Do not catch final validation as recoverable source failure.
- `certificates/sogang-intermediates.pem`: the verified Sectigo OV R36 and GoGetSSL RSA DV SSL CA 2 public intermediates omitted by the source servers. `package.json` supplies it only to `npm run collect` via `NODE_EXTRA_CA_CERTS`.
- `test/collect.test.mjs`: main-site validation, sampling, recovery/bootstrap, all-board output, and persistence failure checks with local responses/temp directories.
- `test/cms.test.mjs`, `test/fixtures/cms-list.html`, `test/fixtures/cms-empty.html`: full comment titles, pins, sparse lists, identity, ordering, malformed input, and incomplete sampling. Fixtures retain public list metadata and remove authors; no article bodies/attachments.
- `test/fixtures/board-list.json`: reduced main-site metadata with Korean titles and pinned/regular ordering.
- `test/fixtures/computing-notices.html`, `test/fixtures/computing-news.html`: observed first-page college lists with authors, views, attachment links, styles and handlers removed. CMS tests cover direct pinned titles, untruncated comment titles, fifteen-row ordinals, source identity, two-page sampling and incomplete second-page rejection.
- `test/certificate.test.mjs`: intermediate fingerprint, CA status, validity, and signature against a Node-trusted root.
- `.github/workflows/publish.yml`: one serialized read-only prepare/conditional-OCR/assemble pipeline, followed by a separate deploy-only job. It uploads only the validated `meal-site/` feeds/meals directories, never work images, models or diagnostic crops.

### Feed and recovery

- Output path: `public/feeds/<source-id>.json`. Envelope: `{ schemaVersion: 2, sourceId, collectionStatus: 'ok' | 'error', lastAttemptAt, fetchedAt, notices: { title, url, publishedDate }[] }`.
- `fetchedAt` is last successful source fetch, not newest publication date. `lastAttemptAt` records the completed attempt, must not precede success, and changes on recovery. Both are canonical UTC ISO timestamps with milliseconds, at most five minutes ahead. Dates are valid `YYYY-MM-DD`; titles are nonempty and at most 2000 characters; entries are unique safe HTTP(S) links without credentials, newest first, at most 30. Strip unknown fields from recovery output.
- Each request has a 20-second timeout, a streamed 2 MiB body ceiling, expected JSON/HTML content type, no redirects/cookies/referrer, and cache revalidation. Collect at most two sources at a time, sequential pages per source, with university request starts at least one second apart across all hosts. The timeout includes any short pacing wait. `paceRequests()` serializes starts with a monotonic clock; abort/network failures do not poison later starts. GitHub baseline/recovery reads also have at most two concurrent requests but do not use the university pacing gate. No blind retries or unbounded pagination.
- Rolling mode validates the entire published baseline from `https://hiyabye.github.io/sogang-notices/feeds/<id>.json` before any university request, then reuses those exact validated values for carry-forward and failure recovery. A missing, unavailable or invalid prior feed stops the run without automatically contacting Sogang or replacing output. Full mode needs no baseline initially and fetches validated published recovery only after an explicitly classified source failure. An attempted failure preserves notices/fetchedAt and sets error status/new lastAttemptAt. Carried boards preserve both timestamps and their existing status, including an older error. Never publish raw exceptions or response bodies; diagnostics belong in logs.
- Missing, wrong-source, malformed, future-dated, or otherwise invalid required recovery stops the entire publication. Explicit full bootstrap therefore requires all 41 sources to succeed; never fabricate empty fallbacks. Healthy boards can publish with recovered failures only when every recovery is valid. Newly added boards have no recovery path until their first successful publication; a missing new-board recovery must preserve all previous output.
- Validate all feeds before writing a staged directory. Write failures stop publication. Rename the previous local feeds directory aside, replace it with the complete stage, and restore the old directory on replacement failure. Clean staged paths; do not describe this as crash-proof or CDN-transactional publication. Output/cleanup/workflow-summary failures must produce a failed command, never continue to upload.
- Console output and `GITHUB_STEP_SUMMARY` identify mode/batch, new attempts, carried boards and actual recovered failures. Carried errors are labeled as previous failures, not attempts in this run. Warn when any fetchedAt is at least 24 hours old, without falsifying freshness or automatically expanding the crawl. Tests pass `summaryFile: null` or an isolated temporary path so synthetic collections cannot pollute the CI job summary. GitHub Pages caching can return older valid data despite revalidation; do not promise a transactional baseline or perfect last-version knowledge.
- Old schema-1 clients/backups are intentionally unsupported by v0.4. Producer and consumer deploy independently; coordinate tests and live verification before separately authorized publication.

## TLS maintenance

- Use `npm run collect`, not plain `node collect.mjs`, to apply the command-scoped two-intermediate bundle. Never change system trust or disable certificate/hostname checks. Preserve the original OV certificate bytes when maintaining the bundle; append only issuer certificates whose CA flags, fingerprints, signatures and validity have been verified against Node-trusted roots. `test/certificate.test.mjs` checks the exact two certificates and script path. No source leaf, private key or new root is bundled.
- The PEM is a public CA certificate, not a secret. README records provenance/fingerprint. If issuer changes or expiry approaches, inspect the chain, obtain the intermediate from the official issuer, verify against Node-trusted roots, and update tests/documentation together.
- No runtime certificate download or insecure fallback. Remove the workaround only after plain Node fetch verifies the server-supplied chain.

## Publishing and scheduling

- Public repository: `Hiyabye/sogang-notices`. Pages source is GitHub Actions, Node 24 on Ubuntu, serialized runs. Workflow default permissions are `{}`; prepare/OCR/assemble get only `contents: read`, checkout disables credential persistence, and only the deploy-only job gets `pages: write`/`id-token: write` plus the `github-pages` environment. Deploy runs no checkout, Node, Python or project code. Its explicit `!cancelled() && needs.assemble.result == 'success'` condition overrides GitHub's implicit success check so a legitimately skipped OCR ancestor does not suppress deployment after successful assembly; failed assembly or workflow cancellation still blocks deployment. Same-run prepared/OCR artifacts have one-day retention; final validation/staging limits publication to JSON feeds and meals. New setup/cache/artifact Actions are pinned to full SHAs checked against their official tags/action metadata.
- Schedule is `17 * * * *` UTC: one rolling batch each hour, targeting one attempt per board about every six hours. `workflow_dispatch` offers `rolling` (default) and explicit `full` bootstrap/repair. Pass the choice through a quoted environment argument, never interpolate untrusted input into shell code; the CLI rejects all unknown modes/arguments before I/O. Pushing does not itself trigger publication, but the next scheduled run uses default-branch code.
- Six stable batches are weighted by expected list-page requests, not board count: current estimates total 18, 17, 18, 17, 18, 17 requests. These estimates account for observed small/pinned boards but are not hard request limits; source-specific pagination ceilings still apply. Keep existing membership when adding boards, assign additions deliberately to balance expected work/hosts, and update coverage/estimate tests. Missing, duplicate or unknown membership is an error before any network work.
- Each rolling run selects the batch with the oldest latest-member lastAttemptAt; fixed batch index breaks ties. Using attempts instead of successes prevents a failing board from monopolizing the schedule. Using the latest member reflects completion of a normally refreshed batch and avoids one older cached member dominating selection. Failed/missed runs do not advance a separate cursor: selection follows what actually reached the published feeds. No modulo-hour slots, catch-up burst, scheduler manifest, persistent local cache, new credential or state service is needed. Six normal successful hourly runs rotate all six batches; extended source/Actions/deployment outages can still breach the daily freshness target.
- Always publish a complete validated feed set. The first deployment, a new board, or a damaged/missing baseline requires an intentional full run and publication; local full output does not initialize GitHub Pages. Transient GitHub failures should be investigated, not hidden by a full crawl. Full mode uses the same pacing and concurrency. Avoid simultaneous manual collectors outside the serialized workflow.
- Tests, collection, recovery, and staging must all pass before upload/deployment. Any failure stops upload, retaining the previous published directory. Rill warns after 24 hours of source staleness; observed historical CDN lifetime is ten minutes.
- Source reuse licensing remains unestablished. Earlier main-site robots guidance allowed crawling; current CMS responses contain malformed server-template text or unavailable HTML. The Computing and Engineering college hosts returned 404 HTML at `/robots.txt`. EE/SSE guidance disallows internal directories, not the selected `/kor/` lists; ME permits public pages but disallows `/api`, `/admin`, `/adm`; SE permits crawling. Only the approved public list paths are requested. This is not reliable permission or a license. Limit collection to public list titles, dates, and links; recheck guidance before expansion.
